# Filmless — техническое направление

Дата: 22.10.2026. Статус: базовый выбор по предложению владельца; дополнительные компоненты рекомендованы, реализация не начата.

## Базовый стек

- Next.js App Router + React + TypeScript — веб-клиент.
- NestJS + TypeScript — единый сервер приложения и игры.
- TanStack Query (React Query) — запросы, мутации и кэш данных HTTP API.
- Zustand — при необходимости общего клиентского состояния; не заменяет сервер игры или Query.

Предложенное дополнение: Socket.IO для комнат, PostgreSQL для постоянных данных, Prisma для доступа к базе, S3-совместимое хранилище для разрешённых изображений. Конкретные версии, провайдер размещения и хранилище выбираются при подготовке проекта; совместимость проверяется установкой, сборкой и интеграционным тестом.

## Почему это подходит

| Вариант                                              | Плюсы для проекта                                                                            | Компромисс                                                                                                  |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Next.js + NestJS                                     | Соответствует предпочтению владельца; постоянный сервер комнат; раздельные границы UI и игры | Два процесса приложения и общие контракты                                                                   |
| Next.js с серверной логикой внутри одного приложения | Меньше отдельных компонентов для обычного каталога/соло                                      | Долгоживущие соединения и жизненный цикл матчей требуют подходящего размещения и дополнительной организации |

Выбран первый вариант. Next.js отвечает за страницы и интерфейс, NestJS — за доменные правила. Не дублировать игровую логику в Next Route Handlers/Server Actions.

## Владение состоянием

| Данные                                                    | Где живут на клиенте                                   | Источник истины      |
| --------------------------------------------------------- | ------------------------------------------------------ | -------------------- |
| Категории, подборки, результаты поиска, завершённые матчи | TanStack Query                                         | NestJS / PostgreSQL  |
| Открытые панели, настройки звука, общий UI                | Zustand, если это требуется нескольким компонентам     | Клиент               |
| Ввод названия, выбранная подсказка                        | Локальное состояние компонента                         | Клиент до отправки   |
| Участники, текущий раунд, показанный этап, очки           | Отдельный Zustand store комнаты с полученными снимками | Только NestJS        |
| Визуальный обратный отсчёт                                | Вычисляется из серверного deadline с поправкой часов   | Серверные timestamps |

Состояние активной комнаты не копировать одновременно в Query и Zustand. Сокет обрабатывается одним слоем подключения комнаты, обновляющим её store. По завершении матча можно инвалидировать Query результатов. Store сбрасывается при смене комнаты. Сохранять локально можно предпочтения интерфейса, но не счёт и не истинное состояние матча.

В Next.js нельзя разделять серверный singleton store между запросами разных пользователей. Store создавать через provider/factory; React Server Components не читают и не меняют его. QueryClient для SSR также изолировать между запросами. [Zustand: Next.js](https://zustand.docs.pmnd.rs/learn/guides/nextjs.html), [TanStack Query: SSR](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr).

Главная и страницы подборок могут использовать Server Components; интерактивный игровой экран — Client Components. SSR не нужен для тиков таймера. [Next.js: Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components).

## HTTP и события игры

HTTP API: каталог, поиск названий, создание комнаты, получение результата. Socket.IO: присоединение, готовность, старт, отправка ответа и обновления состояния. Оба транспорта используют одни доменные сервисы NestJS. NestJS поддерживает Socket.IO через gateways. [Документация](https://docs.nestjs.com/websockets/gateways).

Каждая игровая команда содержит roundId и уникальный commandId. Сервер проверяет участника, полномочия, этап, deadline, паузу 3 секунды и отсутствие уже принятого правильного ответа. Повтор команды возвращает прежний результат, а не начисляет очки ещё раз. Обработку команд одного матча сериализовать, чтобы параллельные ответы не обходили проверки.

Сервер передаёт текущий разрешённый кадр/кроп, номер этапа, deadline, serverTime и ревизию состояния. Клиент отбрасывает устаревшие обновления. При пропуске событий или переподключении запрашивает полный безопасный снимок; гостевая сессия и членство определяются независимо от socket.id. Нельзя рассчитывать только на встроенное восстановление Socket.IO: оно не гарантировано. [Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/).

Не отправлять клиенту правильный ID, будущие подсказки или полный исходный постер до разрешённого этапа. Каталог возможных ответов — отдельная сущность и не содержит связи с текущей загадкой. Подготовка кропов допустима только при соответствующих правах.

## Время и очки

Сервер контролирует начало/конец раунда, смену кадров, расширение лупы и cooldown. Передаёт временные границы; клиент плавно рисует таймер без рассылки каждую миллисекунду. Время ответа учитывается по получению сервером, клиентскому timestamp не доверяем. Формула очков ещё требует выбора и проверки на мобильных сетях.

Автоматическую повторную отправку ответов выполнять только с тем же commandId и обработкой истёкшего раунда. Не использовать подтверждённые клиентом очки как окончательный результат.

## Постоянные данные и поиск

Рекомендуется PostgreSQL: произведения (фильм/сериал/анимация), алиасы названий, источники изображений и разрешения, версии вопросов, подборки, комнаты, участники, ответы и результаты. Для мультсериалов ответ связан с произведением целиком, а не эпизодом.

Для небольшого стартового каталога достаточно поиска по нормализованным русским названиям и алиасам. Для опечаток можно подключить pg_trgm; Elasticsearch на старте не нужен. Результат поиска не является автоматическим признанием правильности ответа. [PostgreSQL: pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html).

Prisma — предлагаемая ORM для схемы и миграций. Расширение pg_trgm и специальные индексы оформлять SQL-миграциями, при необходимости использовать параметризованные запросы. [NestJS: Prisma](https://docs.nestjs.com/recipes/prisma).

## Размещение и устойчивость

Для прототипа: один постоянно работающий процесс NestJS, Next.js, PostgreSQL; один домен с маршрутизацией /api и /socket.io на NestJS упрощает cookies и доступ. Игровой сервер нельзя размещать как короткоживущую функцию без поддержки требуемого жизненного цикла.

Первый прототип может держать активные комнаты в памяти: переподключение браузера поддерживается, падение процесса прерывает матч. Перед публичной бетой требуется сохранение состояния/ответов в PostgreSQL и определённое поведение восстановления либо явной отмены незавершённой партии. Не обещать восстановление после рестарта, пока оно не реализовано и не проверено.

Redis не обязателен для односерверного прототипа. При масштабировании на несколько игровых процессов отдельно решить владение матчем, общее состояние, доставку событий и сессии. Один Redis adapter сам по себе не решает распределённые таймеры и согласованность игры.

## Организация проекта и проверки

Предлагается pnpm workspace: apps/web, apps/api, packages/contracts. Общие типы и схемы сообщений не должны включать серверные секреты и ответы загадок. TypeScript не заменяет валидацию входящих данных в HTTP и WebSocket.

Первый вертикальный сценарий: создать комнату → присоединиться двумя браузерами → запустить один вопрос → ошибиться и получить 3 секунды паузы → правильно ответить → дождаться общего финала → переподключиться и увидеть верное состояние.

Проверять доменные правила отдельными тестами; сценарий двух участников — браузерным тестом. Обязательные пограничные случаи: повтор команды, ответы на границе deadline, одновременные отправки, устаревший roundId, переподключение во время cooldown, отсутствие утечки ответа.

Обновление: создан монорепозиторий Next.js/NestJS с Tailwind и shadcn/ui, контрактами, доменными тестами, схемой Prisma, локальным Compose и проверками Git/CI. Полная сетевая игра ещё не реализована. Выбор источников и практическая проверка контента описаны в CONTENT_SOURCES.md; проверка с ключами остаётся открытой зависимостью.
